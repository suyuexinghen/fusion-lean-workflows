# 用证据改进长期工作流

当用户希望一个项目能持续取题、自验、交接，并从经验中修订工作方法时使用。适合有多轮相似工作、有下游使用者、能保留输入与产物版本的项目。一次性任务可以只取其中的复核方法。这里的“自进化”指团队从实际失败或可核查的外部案例提出可回滚的改动，在本地验证，再用另一份独立输入决定是否采用。

## 第一次进入项目

先检查当前目标、仓库与已有资料、最近一次交付、现有测试、队列和未决问题。找出一个**真实使用者需要作出的判断**，沿着它走通“原始来源 → 可检验的断言或行为 → 公开入口上的复验 → 使用者可读的解释”。反向走一遍：若使用者从说明得到错误结论，能否定位到具体原句、版本、实现或验收条件？

按用户授权交付。设计请求给出一个可执行的首轮计划，实施请求就在现有工程中跑通第一项，复盘请求重放近期案例并给出下一次可证伪的预测。优先复用已有资料库、测试工具、任务系统与 Git 仓库。可以从一个仓库、一个命令、一个读者问题开始。

## 组织三种长期产物

| 产物 | 该放什么 | 谁会反过来约束它 |
|---|---|---|
| 可验证的领域产物 | 公共 API、可重放数据管道、形式化声明、经核查的断言表等。给每个稳定对象一个 ID，注明前提和承诺。 | 来源核对者检查语义；使用者提供会暴露歧义的消费场景。 |
| 给使用者的解释 | 从“我能据此判断什么”起笔，给例子、适用边界、原文定位及绑定的候选版本。Wiki、操作手册和数据字典均可。 | 领域产物限定能声称的范围；读者答错或无法操作会产生下一条需求。 |
| 工作方法及其证据 | 保存任务图、工作规范、评价器、冻结用例和改进决定。领域产物、说明、规则可以同仓不同目录，也可分别版本化。 | 一次真实失败提出改动；保留例和后续候选决定是否采用。 |

来源库供三者引用。检索到的关键词、题录和另一份转述可以生成候选题；发布具体结论时回到可定位的原文、规格或原始观测。记录版本/摘要、页码或字段、单位、适用域与来源关系。按作品、数据供应方、设备或生成机制划分来源家族，防止同一底稿同时充当独立证据和保留例。

## 每个阶段怎么运转

1. **从消费场景取题。** 先处理会误导下游的结论、再选能打通依赖的关键对象。从本地资料库、失败日志和读者问题取候选；记录选入缘由、已覆盖项和游标。写明本阶段的关键命题、一个能使它失败的输入和终点证据。
2. **先固定独立预期。** 来源核对者先给出答案、边界和能区分两种解释的错例。需要证明先后顺序时，用独立提交或时间可核的记录固定它，再让实施者提交对应实现。记录改正后的预期与依据并保存旧版。提交顺序只能证明文件何时进入历史，内容仍须回到来源核验。
3. **用程序管任务，用 Git 管证据。** 在一个权威任务系统中保存稳定 ID、目标、阶段、依赖、写集/共享资源、负责人、验收条件和后继项。程序按依赖原子认领；交接、退修、恢复与状态变更写入有序历史。可执行任务立即续领。详见[阶段设计、角色与状态转换](references/operate.md)。
4. **在真实入口验收。** 冻结输入、产物、依赖和评价器版本。在使用者实际调用的入口运行一般条件、边界、带错对照和保留例。保存命令、期望、实际、退出码及固定证据。分别记录“接口已陈述”“实例已验证”“全部约定条件已验证”“依据不足”等范围，避免由单个例子推到一般结论。
5. **让独立 agent 做需要阅读判断的部分。** 给它冻结来源、读者题和评价标准。先冻结独立答案，再看待审产物，逐条给出处、反例和裁决。遇到实质差异退回作者，继而在新版本复审。直接委派会话即可。机器检验、agent 判断、真实读者反馈和具名签审各有记录。[评审包与执行会话提示词](references/records-and-prompts.md)
6. **从一次交付转入下一项。** 交付携带固定提交和证据引用；新会话能从记录恢复最后通过的命令、首个失败和下一动作。目标终点按原约定逐项核对。只剩外部材料或签审时，记录恢复条件并先处理无依赖的工作。

## 让岗位经验跨会话积累

每个岗位维护自己的方法与判例，下一任按任务角色接手。遇到本地经验解释不了的现象，可联网追到规范、论文、源码或原始日志，把外部方法写成可证伪的本地预测。独立评审者先冻结答案，再接触可能泄露同题结果的材料。采用前分别核对目标是否忠实、产物能否重建、公开入口是否满足独立目标、复核工具共享哪些假设。按具体疑点选择检查，并记录每项实际覆盖面。[岗位学习、验证和交接示例](references/operate.md#从外部案例积累岗位经验)

## 怎样判断工作方法变好了

把“修好本次产物”和“修订工作方法”作为两个独立决定。先沿一次错误找出**本应发现它的那个步骤**。为候选改动写一句预测，例如“新增字段的下一家供应方也会在导入前得到带字段名的诊断”。固定旧评价器与失败样本，在同一候选上比较改前改后，再换一个会触发同一机制且未参与调参的候选。需改变评价器本身时，保留旧版，在同一输入上并列运行，把题集变更另列。按实测选择采用、保留候选或回退，记录理由、恢复版本和下次区分性试验。[对照实验、提升决策与健康观察](references/evolution-and-health.md)

阶段切换或周期复盘时，协调者查看**所有活动目标**，比较上次快照：可领任务有没有长期无人接、结果是否到了使用者、哪类失败在不同候选上复发、上轮改进是否经得起新输入。把最有证据的一项发现关联到现有任务或新增试验。没有新样本时保留待验。只要下游仍能独立工作，就继续推进。

## 落地材料

- 新项目开工或既有工作流有断点时，用[运行手册](references/operate.md)安排首个阶段，用[记录模板](references/records-and-prompts.md)生成该项目的任务和证据包。
- 向团队解释这种模式的来历时，读[Fusion Lean 项目回顾](references/fusion-case.md)。其中的仓库数量、工具、人数、证明目标都是该项目的选择。
- 想先在其他领域走一遍时，读[数据导入示例](references/data-example.md)，从技能目录运行 `python3 examples/replay.py`。这个演练用 Python 标准库，可独立于任何项目资料重放。
